# The Carter-Okafor household's money

Thirteen months — **2025-06-01 to 2026-06-30** — of one Berlin household's
personal spending, across three instruments at two banks and a card issuer, for
Mind My Money to run its money round on. Everything here is fictional, generated
from one seed, and regenerated by one command:

```sh
python3 generate/gen_household.py --seed 42       # the ledger and every view of it
python3 generate/gen_household_photos.py          # the till receipts, reconciled
python3 generate/check_household_fixture.py       # reads it all back
```

The window ends on the demo epoch, so **June 2026 has June 2025 beside it** and
the report's shadow columns have numbers.

## ⛔ What may be seeded into a vault, and what must never be

| | |
|---|---|
| `statements/` | **input.** What a person downloads from their bank. This is what belongs in a demo vault, and nothing else here does. |
| `evidence/` | **the portals' source data.** The end-to-end harness serves these as order histories, a mailbox, a usage page. A person reaches them by signing in, and so must the agent. |
| `receipt-photo-sources/`, `receipt-spec.json` | **input to the photo pipeline.** The paper slips behind the handful of rows nothing online can name, rendered here and composited into the photo library. |
| `PLANTED.md` | **the answer key.** What was planted and what each item costs, measured from the ledger. Seeding it — or leaving it where a session can read it — turns every run into an open-book exam. |

The whole point of the split is that the agent has to *go and get* the evidence.
A fixture that hands over the answers measures nothing.

## The three instruments, and why the exports differ

| file prefix | whose | dialect |
|---|---|---|
| `meridian-everyday-` | Alex's own card | English CSV, commas, `YYYY-MM-DD`, UTF-8 — the same shape as the studio's business export |
| `havelbank-joint-` | the household Girokonto | German CSV, semicolons, `1.234,56`, `TT.MM.JJJJ`, **UTF-8 with a BOM** |
| `nordufer-sam-` | Sam's card at a second bank | German CSV, semicolons, **every field quoted**, **`Soll`/`Haben` in two columns**, `1234,56`, **cp1252** |

**The agent is the parser** — it reads a bank the way a person does, off the
screen or from whatever export the portal offers, with no per-bank integration
anywhere. So the dialects are the point rather than an inconvenience. The BOM turns the first header into a name
no naive reader expects; `cp1252` is what a German bank export actually is; and
splitting the amount across `Soll` and `Haben` puts the sign in *which column it
is in* rather than in the number. A run that only ever meets one well-behaved
UTF-8 CSV has not met a bank.

Each instrument ships **thirteen monthly exports and one whole-window export**.
Both are written in the same run from the same rows, and
`check_household_fixture.py` asserts they add up to each other.

## What is in the year

Roughly **1,050 transactions**: rent, Nebenkosten, Strom, Kita, insurance,
internet, a monthly transport pass, groceries at the counter and by delivery,
two salaries and the transfers between the three accounts, a summer on Usedom,
Christmas, a washing machine on instalments, a spring trip to Amsterdam.

**About one row in twelve is behind a payment rail that does not name the shop.**
Nine fictional rails stand in for the nine shapes a Berlin statement actually
carries — a PayPal-shaped wallet, a Klarna-shaped BNPL bank, a marketplace, a
Rechnungskauf processor, Stripe-, Mollie- and Adyen-shaped processors, a
card-terminal processor, a delivery platform. `generate/household/model.py`
records which real shape each one imitates; the names are invented, and the
descriptors are written the way a German bank prints them, truncations and
reference strings included.

Most of those rows can be resolved from evidence that exists. **A few cannot be
resolved at all**, deliberately: `unnamed` is a real state in the contract, and a
run that names everything proves nothing.

## Where the evidence lives

| file | the portal it feeds | what it names |
|---|---|---|
| `evidence/mail.json` | the household mailbox | the wallet and processor rows, and the letters behind the standing charges — a price rise, a tariff change, a cancellation confirmation |
| `evidence/grocer-orders.json` | the online grocer's order history | every basket, line by line; each order reconciles to one statement row to the cent |
| `evidence/marketplace-orders.json` | the marketplace's order history and memberships | the marketplace rows, and the membership that began as a trial |
| `evidence/bnpl-purchases.json` | the BNPL bank's purchase list | the Rechnungskauf and Ratenkauf rows, which name no shop anywhere else |
| `evidence/streaming-account.json` | the streaming service's account page | two memberships on one household, what each costs, and when each was last watched |
| `evidence/gym-account.json` | the gym's members' area | every check-in, newest first |
| `evidence/photo-evidence.json` | the photo library | the handful of rows whose only witness is a photographed till receipt |

⚠️ **The till receipts move whenever the ledger does**, because the ledger picks
them — a different seed, a wider window or a changed weight chooses different
rows. Everything downstream of that choice is expensive and goes stale in
silence: a rendered scan, a manifest entry, a generated composite, a library
JPEG. `gen_household_photos.py` therefore **reconciles rather than appends** —
it renders exactly the scans the current spec names, deletes the ones it does
not, and rewrites the manifest block between two markers. Its `--check` mode is
folded into `check_household_fixture.py`, so an orphaned composite — a
photograph of a transaction that no longer exists — fails the same command as a
wrong balance.

## Regenerating it

`build.py` holds the ledger and `emit.py` writes the views, so a statement row
and the order history behind it are the same fact rendered twice — they cannot
drift apart. Two instruments enforce that:

- **`build.check()`** recomputes every planted finding while generating and
  **raises** rather than writing a fixture that contradicts `PLANTED.md`.
- **`check_household_fixture.py`** reads the files back — through the cp1252
  decoder, through the BOM, through the German number format — and reconciles
  the balances, the monthly-against-whole-window exports, and every piece of
  evidence against the row it claims. Every check is counted, and a check that
  matched nothing fails.

A different `--seed` gives a different year with the same findings in it; the
asserts are what make that safe to do.

**Rolling the window forward is editing two strings** — `WINDOW_START` and
`WINDOW_END` in `generate/household/model.py`. Nothing else knows the dates: the
month list, the whole-window filenames, the last-month concentration and the
checker's file discovery are all derived. That is deliberate. A synthetic life
that stops eight weeks ago reads as abandoned, and a money round cannot be told
to pretend it is June — it reads the live date off the machine. So the dataset
has to be maintained rather than frozen, and the only version of that which
survives being done every month is a mechanical one.

`MANIFEST.txt` lists what `gen_household.py` itself wrote. The rendered scans
under `receipt-photo-sources/` come from the second step and have their own
`MANIFEST.tsv`.

## What this folder is not

It is a household and the evidence a person could go and find. Putting any of it
in front of an app is somebody else's job and deliberately not described here.
